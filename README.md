# festival-qr-pos

学園祭向けの独自QR決済・POS統合システム。来場者が受付でチャージし、各店舗のPOSでQR決済する。

- 構成:Cloudflare Workers + D1 / Hono / Vite + React + shadcn/ui + Tailwind
- デプロイ:Cloudflare Workers Builds(GitHub 連携)

## 役割

| 役割 | 値 | ログイン方法 |
|---|---|---|
| 全体管理者 | `ADMIN` | ログインID + パスワード |
| 店舗責任者 | `SHOP_MANAGER` | ログインID + パスワード(全体管理者が登録) |
| 店員 | `CLERK` | ログインID + パスワード(店舗責任者が登録) |
| 受付担当者 | `RECEPTION` | 担当者ごとの恒久ログインQR(同時ログインは1端末のみ) |
| 顧客 | `CUSTOMER` | メールアドレス(=ログインID) + パスワード |

パスワードを忘れた場合は、全体管理者(店員は店舗責任者も可)が再設定する。メールは送信しない。

## 開発

```bash
npm install
cp .dev.vars.example .dev.vars   # ローカル用の秘密値(Git には入らない)
npm run db:migrate:local         # ローカル D1 にスキーマを適用
npm run dev                      # 開発サーバー(Vite + workerd)
npm run typecheck
```

初回セットアップは `http://localhost:5173/setup` を開き、`.dev.vars` の `SETUP_TOKEN` を入力して最初の全体管理者を作る。

## 本番へのデプロイ(Workers Builds)

1. D1 は作成済み(`festival-qr-pos`、APAC)。`database_id` は `wrangler.jsonc` に入っているが、**ビルド変数 `D1_DATABASE_ID` を設定すればそちらが優先される**(別アカウントで使うときも、ファイルを書き換えずに済む)。
2. Cloudflare ダッシュボードの **Workers & Pages → Create → Import a repository** でこのリポジトリを接続する。
   - Build command: `npm run build`
   - Deploy command: `npm run deploy:builds`
3. 接続後の **Settings → Build → Variables and secrets(ビルド変数)** に次を登録する。デプロイのたびに `scripts/deploy.mjs` が読み取り、`database_id` の設定・マイグレーション・デプロイ・シークレット登録までを自動で行う。

   | 名前 | 内容 |
   |---|---|
   | `D1_DATABASE_ID` | D1 の database_id(省略すると `wrangler.jsonc` の値) |
   | `SETUP_TOKEN` | 最初の全体管理者を作るときだけ使うトークン。作成後は変数を削除してよい(Worker 側のシークレットは残る) |
   | `PBKDF2_ITERATIONS` | 任意。ハッシュの反復回数。省略すると 10000(無料プラン向け)。有料プランなら 100000 にできる |
   | `R2_BUCKET_NAME` | 任意。カードデザインの背景画像をR2に保存する(10MBまで・縮小なし)。指定したバケットが無ければデプロイ時に作り、`IMAGES` として結びつける。省略するとD1に縮小して保存(約0.9MBまで) |
   | `PIN_PEPPER` | 物理カードPINのハッシュに混ぜる32文字以上のランダム文字列。**後から変えるとPINが全て無効になる。入れたら変えない** |

   変数を入れなかったシークレットは、Worker にすでにある値を変えない。値はコマンドラインやログに出さない(標準入力で渡す)。確認だけしたいときは `DRY_RUN=1 node scripts/deploy.mjs`。
4. デプロイ後に `/setup` を開き、全体管理者を作る。

## セキュリティ上の設計メモ

- パスワードとPINは PBKDF2(SHA-256)。反復回数は既定 10,000(Workers 無料プランのCPU時間10msに収めるため)。有料プランならビルド変数 `PBKDF2_ITERATIONS` で最大 100,000 まで上げられ、保存形式に回数を含むので既存のハッシュはそのまま使える。セッションIDと受付ログインQRのトークンは SHA-256 のハッシュだけをDBに保存する。
- 状態を変える API は同一オリジンの `Origin` ヘッダーを検査する(Cookie は `HttpOnly` / `SameSite=Lax`)。
- 受付ログインQRは担当者ごとに1枚。再発行・失効で古いQRは即時に使えなくなり、その担当者のセッションも破棄される。トークンは過去分を含め再利用しない(`token_tombstones`)。
- 監査ログにはパスワード・PIN・生のQRトークンを保存しない。履歴系テーブルは DB のトリガで更新・削除を禁止している。
