# 仕様 v0.3 変更点(v0.2 への差分)

- 基準日:2026年11月17日
- **優先順位:この文書の記載は `v0.2.md` より優先する。** 記載のない項目は v0.2 のとおり。
- 「決定」=運営者(依頼者)が明示した事項、「仮定」=合理的に置いた仮定(違えば差し替える)。

## 1. 決定事項

### 1.1 構成・提供形態
- Webサイトとして提供し、**PWA化できる**構成にする(v0.2 §24.3 の「PWA対応」は必須へ格上げ)。
- Cloudflare 上に構築する(Workers + D1)。デプロイは **Workers Builds(GitHub連携)**。
- UI は **shadcn/ui + Tailwind**。LINE/Instagram 風の操作感に寄せる。
- 会場回線は Wi-Fi。

### 1.2 認証・アカウント(v0.2 §3, §4, §20)
- メールアドレスは**ログインIDとして使うだけ**。メール送信・メール認証は実装しない。
- パスワードを忘れた場合は**全体管理者が再設定**する。
- 店員アカウントは**店舗責任者が自店舗分を登録**する(v0.2 §8.2 の「全体管理者が店員を設定」を変更)。全体管理者は店舗責任者を設定する。
- **返金は店舗責任者(自店舗)と全体管理者のみ**。店員は返金できない(v0.2 §3.3 のとおり)。

### 1.3 スマホ支払QR(v0.2 §5)
- QRは**読み取って DB 照会や API を使った時点で消費**する(決済成功を待たない)。
- 結果として、確認画面でキャンセル・残高不足になった場合は利用者がQRを作り直す。
- これを実用にするため、QR読み取り時に**決済セッション**(`payment_sessions`)を作る。最終確定はこのセッションに対して行う。
- 決済セッションの有効期間は**5分**(設定値として全体管理者が変更できるようにする)。

### 1.4 物理カードPIN(v0.2 §6.6, §20.3)
- 試行回数制御は**フロントエンドのみ**(v0.2 のとおり。サーバー側のカード単位ロックは入れない)。
- 理由:操作者は店員で、API 利用にも店員ログインが必要なため。

### 1.5 個別クーポン(v0.2 §14.6 を置き換え)
- カードやウォレットへは**紐づけない**。クーポンコードを**店頭で入力**して使う。
- 利用者画面の「個別クーポン一覧」(v0.2 §4.3, §22.1)は不要。物理カード削除時のクーポン引き継ぎも不要。
- 他の割引・共通クーポンとの併用ルールは v0.2 §14.7 のとおり。

### 1.6 払戻し(v0.2 §1.3 を変更)
- 学園祭期間内に、**受付で残高の残金を現金で渡す**払戻しに対応する。
- v0.2 §1.3 の「電子残高からの現金引き出しには対応しない」は、「期間内の受付払戻しを除き対応しない」に読み替える。
- 払戻しは新しい取引種別(`wallet_ledger.kind = 'PAYOUT'`)として残し、受付の現金台帳にも記録する。

### 1.7 受付の現金管理(v0.2 §3.5, §7 に追加)
- **釣銭準備金の入力は不要**。チャージ時に受け取った額と、出金(払戻し)時に渡した額が記録に残ればよい。
- **途中回収**(金庫へ移した額)を記録できる。
- 受付担当者は交代制。**担当生徒1人に恒久のログインQRを1枚**割り当て、QRでログインし、交代時にログアウトする。端末は何台でも使える。
- **ログインQRの保護**:
  1. 全体管理者がQRを**即時失効・再発行**できる(履歴を残す)。
  2. 同じ担当者の**同時ログインは1端末のみ**(新しいログインで古い端末は破棄)。
  - 受付端末の事前登録は**行わない**。
- **締めの単位は全体管理者が設定**できる(日次 / 担当者交代ごと / 手動)。
- 期待現金額 = `チャージ − 払戻し − 途中回収 ± 訂正`。実際に数えた金額の入力は任意で、入力があれば差異を記録する。
- 締めた後の記録は変更できない。誤りは新しい訂正イベントで直す。

### 1.8 店舗への精算
- 精算の運用(現金化の方法)は**ケースバイケース**で、システムでは扱わない。
- ただし、**各店舗(クラス)の分として扱う売上額**(純売上=実支払額−返金額)は**全体管理者が閲覧**でき、CSV出力できる(DBビュー `v_shop_settlement`)。

### 1.9 通信断(v0.2 §20.6)
- 決済そのものはオフラインでは行わない(残高の二重利用を防げないため)。
- 決済確定のリクエストに**リクエストID**を付ける。タイムアウト時は画面に「結果確認中」と表示し、同じIDで状態を照会する。成功・失敗を断定せず、自動で再決済もしない。
- 結果不明の取引は端末側に保存し、解決するまで新しい会計に混ぜない。
- PWA で画面部分をキャッシュし、回線が切れても画面とカートは保持する。
- 通信断時の店舗の運用(販売停止、現金対応など)は**ケースバイケース**で、仕様化しない。

### 1.10 資金決済法
- **前払式支払手段の6か月特例**の範囲で運用する方針。
- ウォレット(残高)と物理カードの有効期限は**発行から6か月以内**に収め、利用者・受付向けに有効期限を明示する。
- 適用条件の最終確認は学校・主催側で行う(本システムは法的判断をしない)。

### 1.11 店員ログイン(2026-11-18 改定。v0.2 §4.2, §20.1 に追加)
- 店員は**ログインID+パスワード**と**ログインQR**のどちらでもログインできる。
- **ログインIDは店舗責任者が設定**する(登録時に決め、あとから変更もできる)。全体管理者も操作できる。
- 店員のログインQRは受付担当者と同じ仕組み(恒久QR、店舗責任者が発行・再発行・失効)。トークンは `FES1:C:` で始まる。
- 受付担当者と違い、**店員は複数端末で同時にログインできる**(レジを複数台並べるため)。
- QRを再発行・失効するとその店員のログイン中の端末は直ちにログアウトされる。IDを変更したときも同様。

### 1.12 定価の一律値下げ(2026-11-18 改定。v0.2 §9.4, §14 に追加。POS・商品実装時に作る)
- **店舗責任者**が自店舗の商品の**定価を一律に値下げ**できる(例:タイムセール)。全体管理者の「全ユーザー対象割引」(v0.2 §14.4)とは別の機能。
- 値下げの設定は、**定率(例:20%引き)または定額(例:1点につき50pt引き)**、開始・終了日時(省略すれば即時・手動停止)。
- 値下げは**リアルタイムに反映**する。店員のPOSと利用者の画面は、数秒以内に新しい価格へ切り替わる。
- 決済側の安全策:
  - 価格はサーバーが**注文を作る瞬間に再計算**する。画面の価格は信用しない。
  - 画面を開いている間に価格が変わっていた場合、会計は**価格変更の通知つきで止め**、店員が新しい合計を確認してからやり直す(古い価格のまま決済されない)。
  - 注文明細には**定価・値下げ後の単価・適用した値下げ**を履歴として残す(過去の注文は変わらない)。
- 売上集計では「定価ベースの売上」と「値下げ額」が分かるようにする。

## 3. 技術方針

- **API**:Cloudflare Workers + Hono(TypeScript)。静的アセットも同じ Workers で配信する。
- **DB**:D1(SQLite)。決済・返金は `db.batch()` で1トランザクション化する。残高・在庫・返金上限・クーポン上限は `CHECK` 制約で超過を拒否する(`migrations/0001_init.sql`)。
- **認証**:Cookie セッション。パスワード・PIN・各種トークンは WebCrypto(PBKDF2 / SHA-256)でハッシュする。PBKDF2 の反復回数は、Workers 無料プランのCPU時間(10ms)に収まるよう既定 10,000、`PBKDF2_ITERATIONS` で最大 100,000 まで変更可(保存形式に回数を含む)。反復が少ない分、パスワードは長く推測されにくいものにする(PINは pepper を HMAC で混ぜるので DB 漏えいだけでは復元できない)。
- **フロント**:Vite + React + shadcn/ui + Tailwind。PWA(Service Worker + Web App Manifest)。表は TanStack Table。
- **QR読み取り**:標準の `BarcodeDetector` を優先し、非対応端末向けに JS ライブラリで代替する(v0.2 §21.1)。

## 4. 実装の進み具合

実装済み(認証・権限・管理):

- 認証(顧客のメール+パスワード、スタッフのID+パスワード、受付のQRログイン)、Cookie セッション、同一オリジン検査
- 役割ごとのサーバー側権限確認(店舗単位の操作は所属店舗のみ)
- 初回セットアップ、店舗管理、店舗責任者・店員・受付担当者の登録、利用停止、パスワード再設定
- 受付・店員のログインQRの発行・再発行・失効(受付は同時ログイン1端末、店員は複数端末可。トークン墓標)
- 店員のログインID変更(店舗責任者)
- 通貨表示・学園祭名の設定、監査ログへの記録

実装済み(レジ決済・スマホQR):

- カート(数量のみ端末に保存。再読み込みや通信断でも消えない)→ 顧客QR読み取り → 支払い確定。QRは読み取った時点で消費される
- 価格・値下げ・在庫は**確定の瞬間にサーバーが再計算**。画面で確認した合計と違えば確定せず、新しい合計を見せて確認し直す
- 決済セッション(既定5分・全体管理者が設定)。期限切れ・取消後は確定できない。カートに買えない商品があるときは、QRを消費する前に断る
- 残高・在庫・注文・台帳・セッションは1トランザクション。残高不足・在庫不足は DB の CHECK 制約が全体を巻き戻す(同時購入でも売り越さない)
- 同じリクエストIDの再送は元の結果を返す(二重決済しない)。通信断で結果が不明なときは、再送せず状態を照会して結果を表示
- 注文明細に、定価・値下げ後の単価・適用した値下げ名を記録
- スモークテスト: scripts/smoke-pay.sh(132項目)。カート・確認・完了・価格変更通知の画面はブラウザ通しテストで確認

実装済み(物理カード):

- 全体管理者のみ: 一括発行(最大100枚・連番のカード番号・バッチ名)、印刷シート、QR読み取りによる有効化(ニックネーム・4桁PIN・期限。PINは自動生成も可)、一覧・検索(ニックネーム・番号・バッチ・状態)、一時停止/解除(理由必須・監査ログ)、PIN再設定、未有効化カードのQR作り直し、削除、再発行(残高の引き継ぎ)
- PINは pepper(PIN_PEPPER)付きのPBKDF2ハッシュで保存。サーバー側のカード単位ロックはなく、3回間違えたらQR読み取りに戻す制限は画面側のみ(§1.4)。PINの違いは監査ログに残る(PIN自体は残さない)
- レジ: カードのQR → PIN入力(数字キー) → 内容確認 → 確定。PINが違えば確定せず、セッションは続く。注文は pay_source=CARD・card_id付き
- 受付: カードを読み取ってチャージ・払戻し(払戻しはPIN必須)
- スモークテスト: scripts/smoke-cards.sh(157項目)。管理者の発行・有効化・停止、レジ・受付のPIN入力はブラウザ通しテストで確認
- 未対応: ウォレット(残高)の6か月期限切れ時の扱い、カード利用者向けの残高照会

実装済み(セット商品):

- 店舗責任者がセットを登録(セット価格・内訳ごとの必須/選ぶ数/重複可・選べる商品と追加料金・値下げ対象)。内訳IDを保って更新できる
- レジでセットを選ぶと内訳の選択画面。必須が埋まるまで追加できない。売り切れの選択肢は無効表示、必須の内訳がすべて売り切れならセットは提供終了。店員はセットの売り切れも切り替えられる
- 決済はサーバーがセット価格・追加料金・値下げ・在庫を再計算。単品とセット内の同じ商品は在庫を合算し、同時購入でも売り越さない。D1の1文100個までの束縛値制限に合わせ、確定時のガードを小分けにした

## 原価・粗利、返金の拡張、注文取消し、監査ログの検索(2026-11-23)

- **番号の付け替え**: 注文ステータス画面で、店員・店舗責任者が番号を直せる(受け渡し済みは不可。監査ログ `order.call_no`)。
- **スマホで見る**: 支払ったお客様のホームに「受け取り待ちの注文」(店名・商品・呼び出し番号。自動も番号札も)を、受け渡しが済むまで表示する。呼ばれたら「呼ばれています」と強調する。アカウントのウォレットに紐づく注文だけが対象で、画面を開いている間だけ4秒ごとに更新する。
- マイグレーション `0010_call_tag.sql`。
- 修正: マイグレーション 0009 の過去ログ補完が、監査ログの更新禁止トリガに止められて本番のデプロイが失敗していたため、補完のあいだだけトリガを外して戻すようにした。

## 呼び出し札の英数字対応・店舗名の変更(migration 0011)

### 呼び出し札
- 札は半角の英数字・記号(スペース不可)1〜8文字。英字は大文字にそろえる(`a-5` → `A-5`)。共通処理は `src/shared/callTag.ts`。
- 保存: 1〜999の数字(先頭0なし)は従来どおり `order_tracking.call_no`、それ以外は `order_tracking.call_label`。表示・重複判定は `COALESCE(call_label, CAST(call_no AS TEXT))`(`007` は `7` と別の札)。
- API の `callNo` は文字列になった(決済結果・店員の一覧・スマホの受け取り待ち・呼び出しボード)。レジの入力は `tag`(文字列)、付け替え `POST /orders/:shopId/:orderId/call-no` の `callNo` も文字列。エラー: `TAG_REQUIRED` / `TAG_INVALID` / `TAG_IN_USE`。
- 呼び出しボードの並びは数字(大小順)→ 英字・記号(文字順)。

### 店舗名の変更
- 店舗責任者(自店舗)と全体管理者が `POST /shops/:shopId/rename`(店舗設定の「店舗名」)。他店と同名は `SHOP_NAME_TAKEN`。`name` と `display_name` は同じ値にそろえる。
- 店舗は不変のIDで結びついているので、注文・返金・監査ログは名前を変えても同じ店舗のまま。
- 変更履歴は追記専用の `shop_name_history`(最初の名前は valid_from=0)。`GET /shops/:shopId/name` で履歴を表示。監査ログ `shop.rename`(before/after)。全体管理者の `PATCH /admin/shops/:id` での名前変更も履歴に残る。
- 過去の記録は「その時点の店舗名」で表示: 監査ログ(画面・CSV)は当時の名前+「現在の店舗名」、お客様の利用履歴は当時の名前。売上集計・お客様向けの店舗一覧などは現在の名前。
- 監査の店舗の絞り込みは店舗IDなので、名前が変わっても同じ店舗で絞り込める。

## 合計0円の会計・顧客のパスワード変更・一覧の検索化

### 合計0円の会計
- クーポン等で合計が0円になる会計も、お客様のQR(またはカード)を読み取って確定できる(従来は「決済は不要です」で断っていた)。クーポンの本人上限・使用済み記録に、お客様の特定が必要なため。

- 注文ステータス(調理中・呼び出し)・呼び出しボード・スマホの受け取り待ちには、0円の注文も出る(「全額返金・取消し済み」の判定から0円の注文を除外)。
- 制限: 0円の注文は返金・取消しの対象にならない(返金額が0のため)。

### 顧客のパスワード変更
- 顧客のホームに「アカウント」を追加。現在のパスワード+新しいパスワード(確認入力あり)で変更。ほかの端末のログインは外れ、いまの端末は残る。監査 `account.change_password`。(APIは既存の `POST /auth/change-password`)

### 一覧の検索化(D1の読み取りの節約)
監査ログと同じ形式: 種類のタブ+検索ボタン、開いただけ・入力しただけでは読み込まない、1回の最大件数あり、続きは「さらに表示」。

## 割引の発動条件・割引をかける範囲(migration 0012)
- 全ユーザー割引・クーポンの作成画面に、既定では畳んだ「詳細設定」を追加(「併用できる」チェックの下)。通常の作成画面はそのまま。
- 発動条件: ①会計金額(従来の「最低注文金額」) ②商品・タグ・セットを N 個以上買ったとき(`discount_conditions`、1割引あたり最大20件)。複数あるときは「すべて満たす(ALL)/どれか1つ(ANY)」(会計金額も条件に含む)。商品の条件は、対象の店舗を1つに決めたときだけ付けられる。タグは、そのタグの商品の個数の合計。
- 割引をかける範囲 `apply_scope`: DEFAULT(従来どおり。対象を指定していればその商品だけ、なければ全体)/ ORDER(会計全体)/ CONDITION(条件にあたった商品だけ。ANY のときは満たした条件の商品だけ)。
- 条件に合わないクーポンは、従来どおり 409(COUPON_INVALID)で理由を返す(例: 「焼きそばを3個以上で使えます」)。
- 割引の設定は作成後に変更できない(停止のみ)ので、確定時の再チェックはこれまでと同じ。
- クーポンの上限欄の表記を「全体の利用上限(合計で使える回数)」「1人あたりの上限(1人が使える回数)」に変更。

## 全体の有効期限・全データ削除・自己退会・利用規約(migration 0013)

### 全体の有効期限(全体管理者のみ)
- 設定 `expiry.global`(日付。日本時間のその日の23:59:59まで)。`PUT /admin/system/global-expiry {date|null}`。今日より後・今日から184日以内。
- 設定すると、**期限内の**ウォレット(ACTIVE/SUSPENDED)とカード(ISSUED/ACTIVE/SUSPENDED)の期限をその日にそろえる(短縮・延長どちらも)。すでに期限切れのものは変わらない。解除しても、そろえた期限は戻らない。監査 `settings.global_expiry`。
- 以後の新規登録・カード有効化/再発行は、従来の期限設定と全体の期限の**早いほう**になる。全体の期限が過ぎたあとは新規登録・カード発行ができない(`SERVICE_EXPIRED`)。
- 期限が切れたウォレットの扱い(支払い・チャージ・QR不可、受付での払戻しは可)は従来どおり。

### 全データ削除(全体管理者のみ)
- `POST /admin/system/reset {phrase:"全データを削除", password}`。全体の期限が切れた**1か月後(その日の終わり)以降**だけ可(未設定・それ前は 409 `RESET_NOT_ALLOWED`)。パスワード再入力と確認文言が必要。
- 消す: 監査ログ・台帳・取引・返金・現金・店舗・商品・クーポン・カード・QR墓標・全体管理者以外の利用者とそのセッション、ほか上記以外のすべてのテーブル(スキーマから動的に取得)。残す: 設定(全体期限の設定だけは外す)・利用規約・全体管理者アカウントとそのログイン。
- 履歴保護トリガ(RAISE ABORT)は、同じバッチの中で外して消し、そのまま作り直す。削除のあとの監査ログには `system.reset`(消した件数)の1件だけが残る。

### 利用者の自己退会
- `POST /auth/delete-account {password}`(顧客のみ)。**残高0のときだけ**(更新文の中で再確認するので、確認後の入金とも競合しない)。残高ありは 409 `BALANCE_NOT_ZERO`。
- データは消さない: `users.status='DELETED'`・`deleted_at`、ウォレットは CLOSED、セッションと未使用のQRは無効化。台帳・注文・監査は残る。管理者のユーザー一覧には出ない。同じメールでの再登録はできない(ログインIDは残るため)。監査 `account.self_delete`。

### 利用規約・プライバシーポリシー
- 全体管理者が編集(`/admin/legal`)。Toast UI Editor(日本語パック、フォントは Noto Sans JP)で書くか、`.md` をアップロード(編集中の本文があれば上書きの確認。保存するまで公開されない)。「利用者への見え方」でプレビュー。
- 保存のたびに新しい版(`legal_documents`、kind+version。古い版は残り、編集欄に読み込める)。本文は100,000文字まで。HTMLタグは表示されない(react-markdown)。監査 `legal.update`。
- 公開ページ `/terms` `/privacy`(未ログインで読める。`GET /settings/legal/:kind`)。公開中は新規登録で同意が必須(`agree`)で、同意した版を `users.terms_version/privacy_version/legal_accepted_at` に記録。トップ・マイページにリンク。

## QRの再表示・印刷デザイン・確認のポップアップ化(migration 0014)
- 受付チャージ/払い戻しと返金の確認は、画面の中ではなくポップアップ(ダイアログ)で出す。
- ログインQR(受付・店員)とカードQRは、AES-GCMで暗号化して保存(`reception_login_qrs.token_enc` / `cards.qr_enc`。鍵は PIN_PEPPER から生成)。何度でも表示・印刷できる。閲覧は監査ログ(`login_qr.view` / `card_qr.view`)。API: `GET /admin/users/:id/login-qr`(全体管理者)、`GET /shops/:shopId/staff/:userId/qr`(責任者・全体管理者)、`POST /cards/qr-batch`(全体管理者・100枚まで)。失効・削除・再発行で古いQRは見られなくなる。**この版より前に発行したQRは保存されていないため再表示できない(`QR_NOT_STORED`)。再発行すれば以後は再表示できる。** PIN_PEPPER を変えると保存済みQRは復号できなくなる。
- 印刷デザイン(`print_templates`、ログインカード用 LOGIN とQRカード用 CARD、各20件まで): 背景画像(縮小・圧縮してD1に保存)+ QR・表示名・ログインID・カード番号などの位置・大きさ・色。画面でドラッグまたは数値で位置合わせし、実寸でプレビュー。印刷シートでデザインを選べ(同じカードを別デザインで再印刷可)、印刷位置のずれを「右へ・下へ(mm)」で補正(端末に保存)。作成・更新・削除は全体管理者、読むのは全体管理者と店舗責任者。全データ削除でも残る。
- カード一覧に「QR表示・印刷」(1枚)と「表示中のカードのQRを印刷」(まとめて)を追加。

## 受付でのカード有効化・クーポン操作・QR読み取り警告・残高照会

### 受付でのカード有効化(チャージ同時)
- 未有効(ISSUED)のカードを受付が読み取ると `POST /reception/lookup` が `CARD_NOT_ACTIVATED`(403)を返し、受付画面が有効化フォームに切り替わる。
- `POST /reception/activate-card`: `{token, nickname, pin(4桁), cashAmount?, requestId}`。有効化(ウォレット作成・カード更新・監査 `card.activate`)は1つの batch。全体の有効期限(`capByGlobal`)・6か月ルールは管理者の有効化と同じ(`lib/cardActivate.ts` を共用)。
- `cashAmount > 0` のときは続けてチャージ(`performCharge`、現金台帳・台帳・監査を従来どおり記録)。チャージだけ失敗した場合も有効化は残り、`chargeError` を返す(画面から「チャージに進む」で続行できる)。
- 同じ `requestId` の再送は、有効化済み+チャージ済みなら前回の結果(`replayed:true`)を返し、二重にチャージしない。
- 確認はポップアップ。ニックネーム・PIN(2回入力)・チャージ額を入力する。

### クーポン(会計)
- 適用できたらコード入力欄を空にする。適用済みのクーポンは表示され、「外す」で取り消せる(未使用なので別のクーポンを使える)。

### QR読み取りの警告ポップアップ
- `QrScanner` に `accept(value)` を追加。種類の違うQRは、読み取り画面(z-50)の上(z-100)に警告ポップアップを出し、OKを押すまで読み取りを止める(`lib/qrKind.ts` の `expectQr`)。
- 例: クーポンの読み取りでクーポン以外のQR → 「クーポン以外のQRコードが読み込まれました」。使用済み・無効なクーポンもポップアップで知らせる。受付・カード管理・ログイン・会計の全スキャナーに適用。

### 残高照会
- `POST /balance/inquiry`(ADMIN / SHOP_MANAGER / CLERK): カードのQRから残高・状態・有効期限・最終利用日時を返す。QR・残高・状態は変わらず、PINも不要。閲覧は監査ログ `card.balance_view` に残る。
- 画面: 全体管理者 `/admin/balance`、店舗責任者 `/shop/balance`、店員 `/clerk/balance`(各「残高照会」タブ)。
- テスト: `scripts/smoke-activate.sh`。

## 途中回収の上限・PINの決め方・デザインエディタ強化

### 途中回収
- 回収できる額は、その受付の「手元にあるはずの現金」(未締めのチャージ − 払い戻し − 回収済み ± 訂正)まで。判定は挿入と同じ文の中で行い(同時操作でも超えない)、超えると 409 `DROP_EXCEEDS_CASH`。失敗した回収は台帳にも監査ログにも残らない。同じ `requestId` の再送は前回の結果を返す。

### PINの決め方(カード発行時に選ぶ)
- `POST /cards/issue` の `pinMode`: `USER`(既定)= 有効化のときにお客様が決める(カードにPIN記入欄「PIN □□□□」を印刷) / `ISSUE` = 発行時にランダムな4桁を決め、カードに印字する。
- `ISSUE` のPINは暗号化(QRと同じ金庫)して `cards.pin_enc` に保存し、有効化までの再印刷で表示できる。有効化すると消す。有効化はこのPINで行うので、有効化のときにPINの入力は要らない(管理者・受付とも)。`USER` では有効化のときにPIN(4桁)が必須。
- `POST /reception/card-info`(受付): 未有効カードのQRから、PINの決め方を返す(状態は変えない)。
- 受付も残高照会ができる(`/reception/balance`、`POST /balance/inquiry` に RECEPTION を追加)。
- 印刷デザインに `pin` 要素を追加(カード用)。保存済みの古いデザインは、読み込み時に標準位置で `pin` が補われる。

### デザインエディタ
- 背景画像もドラッグ・拡縮できる(`imageBox`: カードに対する %。なければ全面)。
- 要素・画像は選ぶと周りに8点のハンドルが出て、大きさを変えられる(角=縦横比を保って拡縮、QRは常に正方形、文字は左右=枠の幅・上下=文字サイズ)。
- ドラッグ・リサイズ中は、カードの中央・端・ほかの要素の中央・端に吸着してピンクのガイド線が出る(Altで吸着オフ)。矢印キーで微調整。
- レイヤー: 要素の重なり順(配列の順)を手前・奥へ入れ替え、表示・非表示を切り替えられる。背景画像はいちばん奥。
- 「カード管理 → デザイン」タブで、カード・ログインカードのデザインを発行の前に作れる。
- XMLの書き出し・読み込み(仕様: `docs/spec/card-design-xml.md`)。

### 背景画像のR2保存と上限の引き上げ
- ビルド変数 `R2_BUCKET_NAME` を設定すると、背景画像をR2(`IMAGES` バインディング)に保存する。バケットが無ければデプロイ時に作る。未設定なら従来どおりD1に縮小して保存(約0.9MB)。どちらの環境でもコードは同じで、`GET /print-templates/storage` で `{mode: "r2"|"inline", maxBytes}` を返す。
- R2モード: 画像は縮小せず1枚10MBまで(`IMAGE_R2_MAX_BYTES`)。`POST /print-templates/images`(全体管理者)で画像本体を送り、返ったキーを `imageKey` としてデザインに保存する。種類(PNG/JPEG/WebP)と先頭のバイト列を検証。`GET /print-templates/images/:key` で配信(全体管理者・店舗責任者のみ、`nosniff`)。
- 画像を差し替える・デザインを消すと、どのデザインからも使われなくなった画像はR2から消える。`print_templates.image_key`(マイグレーション 0016)。既存のD1保存(data URL)のデザインもそのまま使える。
- XMLの読み込み: エディタが開くだけで、通信しない。**保存ボタンを押したときに初めて** 画像をアップロードする。XMLの上限はR2モードで15MB。書き出しはR2の画像もbase64で埋め込む。

## メニュー画像・マイページの店舗一覧・責任者の追加

### メニュー画像
- 商品・セットに画像を付けられる(追加・変更・外すが可能)。商品編集・セット編集の「画像」欄から選ぶと、ブラウザで縮小(長辺1800px以内・約700KB以下のJPEG)し、**保存ボタンを押したときに** アップロードする。

- 全体管理者は、店舗一覧の「責任者を追加」から既存の店舗に店舗責任者を追加できる(現在の責任者の一覧つき)。`GET /admin/shops/:id/managers` と既存の `POST /admin/users/shop-manager`。
